# 架构说明

CXNP Backend 当前是单 Maven 工程、按业务模块分包的单体应用，不拆分为多个 Maven Module，也不作为微服务部署。

## 分层

- Controller：接口入口、参数校验和响应封装
- Service：业务规则、事务控制和数据权限校验
- Mapper：数据库访问接口
- Mapper XML：动态 SQL 和复杂查询
- Entity：数据库实体
- DTO：请求对象
- VO：响应对象

## 业务模块

- `party`：党员业务
- `rbac`：用户、角色、功能权限和数据权限
- `organization`：党组织和支部业务
- `common`：统一响应、异常、常量和通用工具
- `config`：框架配置

## 认证会话策略

认证使用 Redis 保存不透明 Bearer Token：`login:token:<token>` 指向用户 ID，`login:user-tokens:<userId>` 维护该用户的有效会话集合。同一账号允许多端并存；当前会话登出只撤销当前 Token，拥有 `rbac:user:session:revoke` 功能权限的用户可撤销目标用户全部会话。

会话初始有效期为两小时，受保护请求在剩余有效期不超过 30 分钟时将 Token 与用户会话集合一并续期。每次校验还会复核账号状态；账号停用或会话撤销后，后续请求返回统一的 `401` 响应。

登录失败状态同样存储在 Redis。按标准化登录标识连续失败 5 次后临时锁定 15 分钟，锁定期间不执行密码校验；成功登录会清除失败状态。普通认证失败使用 `401`，临时锁定使用统一 `Result` 结构的 `429`，两者均不泄露账号是否存在。

## 变更与文档架构

项目将长期规则、当前协作状态和单次变更规划分开维护：

| 层级 | 位置 | 职责 |
| --- | --- | --- |
| 长期工程规则 | `AGENTS.md` | 项目定位、技术栈、分层、权限、数据库和协作约束。 |
| 当前协作状态 | `current-task.md` | 当前唯一活跃任务、当前 OpenSpec change、当前任务项和人工确认状态。 |
| 变更规划 | `openspec/changes/<change-name>/` | 每次未归档中大型变更的 Proposal、Specs、Design 和 Tasks。 |
| 稳定业务规格 | `openspec/specs/` | 经验收、同步后的系统业务行为规范。 |

`current-task.md` 不保存已完成任务历史；已验收变更由 Git 历史和 OpenSpec 归档保留。

## OpenSpec 工作流

以下需求必须先建立 OpenSpec 变更包：跨模块或跨层实现、RBAC/认证/数据权限、数据库迁移或多表写入、接口行为变化，以及需要多种验收场景的业务需求。小型、独立且不改变业务语义的修复可以不建变更包，但仍必须具有明确的完成标准。

工作流为：探索（可选）→ 规划 → 人工审阅 → 单项实施与验证 → 人工验收 → 同步与归档。

- 规划阶段生成 Proposal、Specs、Design 和 Tasks，不直接开始实现。
- 每次实施只执行一个未完成任务；验证完成后停止，等待用户明确确认才可继续。
- 发现需求、范围或设计变化时，先更新变更工件并重新确认。
- 所有任务完成后，只有在用户明确验收并允许后，才可同步规格或归档。

## SQL 脚本目录

| 目录 | 职责 |
| --- | --- |
| `sql/` | 项目唯一实际使用的 SQL 脚本目录，包含从历史 `database/` 收拢的建表、基础数据、初始化、测试初始化和测试清理脚本，以及后续新增脚本。 |
| `database/` | 历史保留副本，不作为数据库执行或维护来源。 |

新的业务变更涉及 SQL 时，脚本必须放入 `sql/`；执行、维护和验证数据库脚本时统一以 `sql/` 为准。
