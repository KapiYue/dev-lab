# Design

## Context

参见 [proposal.md](proposal.md)。项目是单 Maven 工程，已经以 `AGENTS.md` 记录长期技术约束，并以 `current-task.md` 管理当前任务。OpenSpec 已初始化为仓库本地的 `spec-driven` schema，并已为 Codex 安装核心工作流能力。

当前 RBAC 数据权限任务已经由用户明确验收。它是在引入 OpenSpec 前完成的，不应为补齐流程而反向创建变更包或改动其业务实现。

## Goals / Non-Goals

**Goals:**

- 建立长期工程约束、当前人工协作状态、变更规划工件之间的唯一职责边界。
- 对中型及以上变更建立“计划审阅 → 单项实施 → 验证 → 人工验收 → 归档”的固定节奏。
- 将未来新增的初始化、测试初始化和测试清理 SQL 统一放入 `sql/`，不破坏现有数据库脚本。
- 让 Codex 能在项目内发现并使用 OpenSpec 核心工作流。

**Non-Goals:**

- 不迁移、重命名或删除 `database/` 中的既有脚本。
- 不回填当前已验收的 RBAC 数据权限任务的 OpenSpec proposal、design 或 tasks。
- 不修改业务 API、数据库表、认证授权逻辑或测试实现。
- 初期不启用 OpenSpec 的扩展工作流；`verify` 继续作为每个任务明确列出的验证要求，而非独立命令依赖。

## Decisions

### 1. 采用仓库本地 OpenSpec 与核心工作流

`openspec/` 跟随代码版本控制，使用默认的 `spec-driven` schema 和 Codex 的核心能力（explore、propose、apply、update、sync、archive）。

选择仓库本地而不是独立规划仓库，因为项目当前是单体、单团队学习项目；需求、设计与实现需要在同一次代码审查和版本历史中关联。只有未来出现多仓库共享规划的需求时，才评估 OpenSpec store。

不在当前阶段启用扩展工作流。替代方案是立即加入 `verify` 等全部命令；这会增加学习路径和操作分支，当前的任务清单与自动化验证已足够承载验证要求。

### 2. 文档职责保持三层分离

| 层级 | 载体 | 唯一职责 |
| --- | --- | --- |
| 长期规则 | `AGENTS.md` | 架构、代码分层、权限与数据库约束；何时使用 OpenSpec；人工确认硬规则。 |
| 当前状态 | `current-task.md` | 当前唯一活跃任务、当前 OpenSpec change、当前任务项、等待的人工决定与完成标准。 |
| 变更工件 | `openspec/changes/<change-name>/` | 本次变更的 Why、业务规格、技术设计、可执行任务和验收场景。 |
| 已确认规格 | `openspec/specs/` | 已归档变更同步后的稳定业务行为；不记录工具或纯文档变更。 |

`current-task.md` 不保存已完成任务历史。当前任务切换时，已验收的内容仅保留在 Git 历史中；新文件只描述新的活跃任务。

### 3. 以变更规模决定是否使用完整 OpenSpec

下列情况必须先创建 OpenSpec 变更包：跨模块或跨层实现、RBAC/认证/数据权限、数据库迁移或多表写入、接口行为变化、需要多种验收场景的业务需求。

单字段修改、独立的小型 SQL 修复、无业务语义变化的格式或注释调整可以不创建变更包；但仍应在 `current-task.md` 或用户明确指令中拥有可验证的完成标准。

### 4. 人工审批规则由 `AGENTS.md` 和 OpenSpec 配置双重声明

OpenSpec 的任务清单是计划工具，不能自身强制阻断 AI。项目规则与 `openspec/config.yaml` 都需要声明以下行为：

1. 变更工件完成后，先等待用户审阅和明确允许实施；不得直接 apply。
2. 每次 apply 只执行一个未完成任务项；完成该项的实现和验证后停止。
3. 只有用户明确回复继续，才能开始下一项；发现范围或设计变化时先更新变更工件并重新审阅。
4. 所有任务完成后，等待用户明确验收；只有用户明确允许归档，才能 sync 或 archive。

双重声明的原因是 `AGENTS.md` 面向所有协作行为，OpenSpec 配置面向其生成的工作流。它们提供行为约束，而非替代用户审批。

### 5. SQL 目录采用渐进迁移

从本变更完成后，所有新增初始化、测试初始化和测试清理 SQL 均写入 `sql/`。`database/` 保持为已有脚本存放位置，既不移动也不删除文件，避免改变当前开发环境的执行顺序。

项目 README 和架构文档将说明这一约定及过渡状态。未来如需统一历史脚本，另建一个带可重复数据库验证的独立变更。

## Risks / Trade-offs

- [规划文档与实现不同步] → 在每个任务完成后只勾选已验证任务；设计变化必须先更新变更工件。
- [OpenSpec 对小改动形成负担] → 仅对中型及以上变更强制使用，具体准则写入长期协作规则。
- [自动化工作流连续执行多个任务] → 将单任务停止、明确继续和显式归档写入项目规则与操作指引，并在每次 apply 前复述当前任务项。
- [旧 `database/` 与新 `sql/` 并存造成混淆] → 文档明确新增文件只进 `sql/`；历史迁移另行规划，不在本变更中进行。

## Migration Plan

1. 已完成：安装 OpenSpec CLI、在项目根目录创建 `openspec/`，并配置 Codex 核心工作流。
2. 更新长期协作规则、OpenSpec 项目上下文、README 和架构文档。
3. 将当前任务切换为本次 OpenSpec 接入任务，并记录它是工具与文档治理变更。
4. 验证 OpenSpec 根目录、Codex 工作流文件、配置解析和文档链接；不运行或变更业务代码。
5. 用户验收后，归档本变更；下一项中型业务需求开始按新节奏创建变更包。

**Rollback:** 删除本次新增的 `openspec/` 与 `.agents/skills/openspec-*` 文件，并还原本次文档修改即可；不涉及业务数据或数据库迁移。
