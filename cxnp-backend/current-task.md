# 当前任务：RBAC 数据权限校验

> 状态：待开始

在已有登录认证、当前用户上下文和功能权限校验的基础上，建立基于角色的数据权限能力。数据范围必须由当前登录用户的角色配置推导，不能依赖前端传入的组织或支部范围。

本批任务以 MySQL 和 Service 层校验为准，不引入 Redis 存储或缓存业务数据。Redis 的缓存键、失效策略及权限变更后的缓存一致性，作为下一批独立任务处理。

## 目标

建立“用户 → 角色 → 数据范围 → 组织/支部 → 业务数据”的授权链路，并在党员查询等业务 Service 层完成数据权限二次校验。

目标链路：

当前登录用户 → 用户角色 → 角色数据范围 → 可访问组织/支部 → 党员业务数据

## 待办

- [ ] 明确数据范围模型与枚举：全部数据、本组织及下级组织、指定组织/支部、仅本人等必要范围。
- [ ] 设计并创建角色数据范围及角色—组织/支部范围关联表，补充唯一约束和查询索引。
- [ ] 在 `sql` 目录补充数据权限初始化数据与测试清理脚本。
- [ ] 增加数据范围相关 Entity、Mapper、DTO/VO 和 MyBatis XML 查询。
- [ ] 实现当前用户可访问组织/支部范围查询 Service，并由 Service 基于当前用户角色推导范围。
- [ ] 在党员列表、详情等业务 Service 中接入数据范围过滤与二次校验，不接受前端传入范围作为授权依据。
- [ ] 区分“无功能权限”和“有功能权限但无数据范围”的错误场景，统一返回明确错误 JSON。
- [ ] 对涉及角色数据范围及指定组织/支部绑定的多表写入增加事务控制。
- [ ] 验证有功能权限且有数据范围时可访问授权数据。
- [ ] 验证有功能权限但无数据范围时不可访问业务数据。
- [ ] 验证越权组织/支部查询、详情访问和前端伪造范围参数均被拦截。
- [ ] 验证重复数据范围绑定的 Service 校验、数据库唯一约束及多表写入失败时的事务回滚。

## 完成标准

- [ ] 数据范围及角色—组织/支部关联关系具备清晰的数据模型、唯一约束和查询索引。
- [ ] 业务数据可访问范围完全由当前登录用户的角色配置推导。
- [ ] 有功能权限且数据范围匹配的用户只能访问被授权的党员数据。
- [ ] 有功能权限但无数据范围、或访问范围外数据的用户均无法获取业务数据，并收到统一错误 JSON。
- [ ] 已完成有数据范围、无数据范围、越权访问、重复绑定和事务回滚场景验证。
